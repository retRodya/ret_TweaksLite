# Архитектура

Как устроено ядро и как добавить модуль или твик. Что строим и почему —
в `docs/VISION.md`.

## Файлы

Порядок загрузки задаёт `.toc`:

| Файл | Что делает |
| --- | --- |
| `Core.lua` | Метаданные из `.toc`, сохранённые настройки, реестр модулей, запуск включённых модулей и твиков. |
| `Window.lua` | Окно: список слева (General, группы, модули с чекбоксами), рабочая область справа (твики чекбоксами, их настройки ползунками), кнопки отката, кнопка Reload UI. |
| `EntryPoints.lua` | Как открыть окно: `/rettl`, `/rettweakslite`, Addon Compartment, страница в Settings → AddOns. |
| `Modules/<Module>.lua` | Один модуль и его твики. Ядро о нём ничего не знает: модуль сам регистрируется. Сейчас: `Tooltips`, `Nameplates`, `UnitFrames`, `Debug`. |

Все файлы общаются через `ns` — таблицу, которую WoW передаёт каждому файлу аддона
вторым значением `...`. Глобальных имён у аддона три: `ret_TweaksLiteDB`
(сохранённые настройки), `RetTweaksLiteFrame` (окно, имя нужно для закрытия по Esc)
и `RetTweaksLite_OnAddonCompartmentClick` (имя из `.toc`).

## Модуль и твики

```lua
local _, ns = ...

ns.RegisterModule({
    key = "Tooltips",                  -- уникальный id и ключ в настройках; не менять
    category = "Interface",            -- группа в списке слева
    title = "Tooltips",                -- строка в списке и заголовок страницы
    description = "Tweaks for the game tooltip.",
    -- Start = function(module) end,   -- необязательно: один раз после входа, если модуль включён
    tweaks = {
        {
            key = "HealthBarAboveTooltip",
            title = "Health bar above tooltip",
            description = "Shows the unit health bar above the tooltip instead of below it.",
            Apply = function(enabled) end,
        },
        {
            key = "ShowAuras",
            title = "Show auras",
            description = "...",
            Apply = function(enabled) end,
            settings = {                -- необязательно: ползунки под твиком
                {
                    key = "AuraSize",   -- уникальный в твике, ключ в настройках
                    title = "Aura size",
                    description = "...",
                    min = 10, max = 40, -- step = 1 по умолчанию
                    default = 17,
                },
            },
        },
    },
})
```

Два правила, из которых следует всё остальное:

- **Модуль включается и выключается только через `/reload`.** Выключенный модуль
  ничего не делает: `Start` и твики не вызываются. Поэтому код, который нельзя
  отменить (например, хуки `hooksecurefunc`), живёт в `Start`.
- **Твик применяется сразу.** `Apply(true)` включает его, `Apply(false)` возвращает
  всё как было. После входа ядро вызывает `Apply(true)` для работающих твиков.
  Твики по умолчанию выключены.

### Дочерние твики

Твик с полем `parent = "<key>"` — дочерний: он уточняет более ранний твик того же
модуля. Сейчас ни один модуль ими не пользуется. Механизм проверен в игре
на твике Target of target in reaction color, который потом убрали (см. журнал
решений в VISION.md).

- **Включён** — его галочка (`ns.IsTweakEnabled`). Она сохраняется, даже когда
  родитель снят.
- **Работает** — включён он сам и все родители над ним.
- Окно показывает дочерний твик под родителем с отступом и только пока родитель
  отмечен. Строки ниже поднимаются, когда он скрыт.
- `Apply(active)` ядро вызывает при каждой смене «работает». Сначала у тех, кто
  перестал работать, от детей к родителям, потом у тех, кто начал, от родителей
  к детям. Поэтому модуль может считать: если работает дочерний твик, родитель
  уже работает.

### Настройки твика

Поле `settings` — список числовых значений, которые уточняют твик. Окно рисует
каждое ползунком под твиком, с тем же отступом и по тому же правилу видимости,
что у дочернего твика: пока твик отмечен.

- Твик читает значение через `ns.GetSetting(moduleKey, tweakKey, settingKey)`
  каждый раз, когда рисует. Отдельного «применить настройку» нет: новое значение
  действует со следующей отрисовки. Если твику понадобится применять значение
  сразу (например, CVar), контракт расширится вместе с ним.
- Сохранённое значение вне диапазона `min`–`max` или не число считается
  значением по умолчанию: так настройки переживают смену диапазона без миграции.
- `ns.SetSetting` прижимает значение к диапазону.

Чтобы добавить модуль: создать `Modules/<Module>.lua`, вписать его в `.toc`
после файлов ядра и перезапустить клиент — новый файл `/reload` не подхватывает.
General всегда первым, дальше группы в порядке файлов в `.toc` (порядок задаёт
первый модуль группы), внутри группы модули по алфавиту. Поэтому `Modules\Debug.lua`
стоит в `.toc` последним: группа Developer остаётся внизу списка.
Группа появляется в списке сама, как только в ней зарегистрирован хотя бы один модуль.

### Общий код модулей

Если двум модулям нужен один механизм, модуль, которому он принадлежит, отдаёт его
через `ns`. Пример — `ns.NameplateNames` в `Modules/Nameplates.lua`: им пользуется
и Nameplates, и Debug. Механизм только набор функций: сам по себе он не создаёт
фреймы и не ставит хуки. Хук ставит `Start` того модуля, который включён,
и только один раз (`NameplateNames.Hook`). Поэтому тест в Debug работает,
даже если модуль Nameplates выключен.
Когда твиков в модуле станет много, их можно разнести по файлам в `Modules/<Module>/`.

Если модуль меняет то, что переживает перезагрузку (CVar), он сам запоминает исходное
значение и возвращает его. Такого модуля пока нет, механизм появится вместе с ним.

## Два состояния модуля

- **Выбрано** — галочка в списке, хранится в `ret_TweaksLiteDB`: `ns.IsEnabled(key)`.
  Клик по чекбоксу сразу пишет сюда.
- **Работает** — каким модуль был при загрузке интерфейса: `ns.IsRunning(key)`.
  До следующего `/reload` не меняется.

Из этих двух состояний окно выбирает, что показать на странице модуля:

| Работает | Выбрано | Рабочая область |
| --- | --- | --- |
| нет | нет | «Check the box to enable …» |
| нет | да | «Type /reload to enable …» |
| да | нет | «Type /reload to disable …» |
| да | да | твики |

`ns.IsPending(key)` — состояния различаются. Пока такой модуль есть, внизу окна
видна кнопка Reload UI.

## Откат

Кнопка отката сравнивает текущее значение с тем, с которым загрузился интерфейс:

- модуль — `ns.IsPending(key)`, откат `ns.UndoModule(key)` возвращает галочку
  к `ns.IsRunning(key)`;
- твик — `ns.IsTweakChanged(moduleKey, tweakKey)`, откат `ns.UndoTweak(moduleKey, tweak)`
  возвращает значение из снимка и сразу применяет его через `Apply`;
- настройка — `ns.IsSettingChanged(moduleKey, tweakKey, settingKey)`, откат
  `ns.UndoSetting(moduleKey, tweakKey, settingKey)` возвращает значение из снимка.

Снимок твиков и настроек делается в `ADDON_LOADED`, сразу после загрузки
сохранённых данных.

## Запуск

1. WoW выполняет файлы аддона по порядку `.toc`. Модули регистрируются.
2. `ADDON_LOADED` — настройки загружены: проверяется версия схемы, выполняются
   миграции, запоминается снимок твиков для отката.
3. `PLAYER_LOGIN` (после входа и после каждого `/reload`) — у включённых модулей
   вызывается `Start`, затем `Apply(true)` у включённых твиков. Каждый вызов
   изолирован: ошибка попадает в BugSack, остальные модули и твики запускаются.

Окно создаётся при первом открытии, а не при загрузке: пока игрок его не открыл,
оно не стоит ни памяти, ни времени загрузки.

## Сохранённые настройки

```lua
ret_TweaksLiteDB = {
    schemaVersion = 1,
    modules = {
        Tooltips = {
            enabled = true,
            tweaks = { HealthBarAboveTooltip = true, ShowAuras = true },
            settings = { ShowAuras = { AuraSize = 17, OwnAuraSize = 21 } },
        },
    },
    collapsed = { Interface = true },   -- свёрнутые группы в списке
}
```

Настройки общие на аккаунт. `schemaVersion` — версия структуры. Если структура
меняется, `SCHEMA_VERSION` в `Core.lua` растёт на 1, а в `migrations` появляется
функция, которая переводит старые данные в новый вид. Так настройки игроков
переживают обновления аддона.

Миграция 1 очищает данные без версии схемы. Такие данные оставила старая
версия аддона 1.0.0 с тем же именем `ret_TweaksLiteDB`.

## Находки об API

- Окно собрано так же, как список аддонов Blizzard (`Blizzard_AddOnList`):
  `ButtonFrameTemplate`, `ButtonFrameTemplate_HidePortrait`, `SetTitle`,
  текст кнопки — глобальная строка `RELOADUI`.
- Чекбокс — `MinimalCheckboxTemplate`, как в списке аддонов Retail. Если клиент
  его не знает (проверка `C_XMLUtil.GetTemplateInfo`), берётся `UICheckButtonTemplate`.
- Список слева повторяет список категорий окна Settings: атласы `Options_List_Active`
  (выбрана) и `Options_List_Hover` (под мышью), шрифты `GameFontHighlight`
  и `GameFontNormal`. Подсветка при наведении проверяется через `IsMouseOver()`,
  а не флагом из `OnEnter` и `OnLeave`: когда мышь переходит на чекбокс внутри
  строки, строка получает `OnLeave`, хотя курсор всё ещё над ней.
- Исходники клиента Forever (1.60.1, `## Interface: 16001`) лежат в ветке `forever`
  репозитория Gethe/wow-ui-source, Retail — в ветке `live`. Шаблоны окна
  (`ButtonFrameTemplate_HidePortrait`, `MinimalCheckboxTemplate`, `SetTitle`,
  `RELOADUI`) есть в обоих.
- Ползунок настройки — `MinimalSliderWithSteppersTemplate`, как в окне Settings
  Retail, значение справа (`MinimalSliderWithSteppersMixin.Label.Right`). Шаблон
  одинаковый в Retail и Forever. Колбэк `OnValueChanged` приходит и тогда, когда
  значение ставит сам код, поэтому окно сохраняет значение, только если оно
  отличается от сохранённого.
- Кнопка «+/−» у группы — те же текстуры, что в списке Settings:
  `Interface\Buttons\UI-PlusButton-*` и `UI-MinusButton-*`.
- Кнопка отката — атлас `common-icon-undo`, им же помечена кнопка Undo
  в окне трансмогрификации.
- Окно Settings нельзя закрывать из кода аддона: `SettingsPanel:Close()` применяет
  игровые настройки, а вызов из нашего кода заражает их taint. Поэтому наше окно
  открывается поверх Settings: strata `DIALOG` выше, чем `HIGH` у Settings.
